\section{Project Folder and Module Structure}

The implementation is cleanly separated into specialized Python modules to adhere strictly to the separation of concerns software paradigm:

\begin{itemize}
    \item \textbf{app.py:} The main Flask application instance, handling HTTP REST requests, file uploads, and session management.
    
    \item \textbf{parser.py:} Encapsulates the PyPDF2, docx, and Tesseract routing logic, managing the file reading operations.
    
    \item \textbf{nlp\_engine.py:} Contains the SpaCy models, regex ontology dictionaries, and the core text normalization functions.
    
    \item \textbf{matcher.py:} Houses the scikit-learn TF-IDF mathematical computations and the weighted scoring formula logic.
    
    \item \textbf{xai.py:} Contains the Explainer class that translates the matcher.py output dictionaries into plain-English string representations.
    
    \item \textbf{database.py:} Manages the SQLite database schema for secure recruiter authentication.
\end{itemize}

\section{Backend Routing and Concurrency}
Upon clicking the upload button by the user of the HR portal, a multipart form gets sent by the user to the upload route, where the target Job Description and an array of resumes represented by file streams are sent. What follows is the creation of an asynchronous thread in the background to perform the required tasks. Were there 100 resumes in the batch, processing of all of them simultaneously on the primary thread would lead to time-out of the request. The asynchronous thread would execute:

\begin{center}
\texttt{parser.py} \(\rightarrow\) \texttt{nlp\_engine.py} \(\rightarrow\) \texttt{matcher.py} \(\rightarrow\) \texttt{xai.py}
\end{center}

At the same time, the frontend makes polling requests to the status of the backend, and upon completion, the finalized array of JSON objects is posted to the dashboard.

\section{Database and Authentication}
SQLite and SQLAlchemy are utilized for lightweight local storage capabilities. These help support recruiter user profiles, authentication, and state per session without using an external database server. SQLite is well suited for a prototype since it can be easily erased for fresh runs, and it provides sufficient functionalities. In addition, authentication ensures access control over upload and results routes for confidentiality reasons.

\section{Frontend Interface and Visualization}
The frontend is designed with the Bootstrap framework to give a sleek Software-as-a-Service look for enterprise use.

\begin{itemize}
    \item \textbf{Upload Screen:} Contains features such as draggable HTML5 sliders, which give recruiters the ability to manually tune the weighting formula prior to computation depending on the type of job role being filled, for example assigning greater importance to soft skills than technical skills for managerial positions.
    
    \item \textbf{Result Screen:} Displays results in the form of a ranked list sorted from the highest-scoring candidates downward. An additional screen presents a Matplotlib/Chart.js radar graph representing the candidate's proficiency across the four scoring metrics: Technical Skills, Soft Skills, Experience, and Context.
    
    \item \textbf{XAI Expansion Panel:} Clicking on a candidate reveals an accordion displaying the exact text generated by the AI algorithm, detailing the missing skills, matched skills, and bonus skills identified.
\end{itemize}

\section{Known Implementation Constraints}
At the moment, the system employs the SQLite database, which suffices well for the prototype. However, it encounters write locks whenever there is high concurrency in enterprise-level batch jobs. Moreover, the skill ontology implemented in \texttt{nlp\_engine.py} is hardcoded in form of a dictionary list. In a production environment, the skills ontology should be associated with a graph database that is remotely updated.
